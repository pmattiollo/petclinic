## Ground truth I verified (so we don't re-argue it)

**Backend** — `OwnerRestController.listOwners` returns a bare `List<OwnerDto>` today; there is
**no `Pageable`/`Page` anywhere in the whole repo**. All four repositories extend the bare
`org.springframework.data.repository.Repository`, so `findAll(Pageable)` is *not* inherited —
a paging method must be declared explicitly (which does work on a plain `Repository`).

**Data** (live DB, 28 owners):
- `last_name` has 26 distinct values → **Potter ×2** (Harry, Beatrix), **Darling ×2**
  (George, Wendy). A sort on name without a tiebreaker is non-deterministic across pages.
- `city`: 20 distinct, London ×6, Hogsmeade ×3.
- `telephone`: 1 NULL (Kevin McCallister). `email`: NULL for all 28 (and absent from the DTO).
- `pets` per owner: 0, 1 or 2 — two owners (James Bond, Hercule Poirot) have none.

**The `owners` table has no index at all** beyond the PK. `V1__core_owners_pets.sql` creates it
bare; `DB.sql` shows indexes on `pets`, `types`, `specialties`, `visits`, `vets` — none on `owners`.

**Everything that assumes a JSON array** and will break when the envelope lands:
- `OwnerTest.search()` — `new TypeReference<List<OwnerDto>>() {}`
- `owners.feature` → `the response JSON array has size 2`, plus `OwnerSteps`'
  `jsonPath().getList("$")` and `getList("lastName", …)`
- `OwnerSearchThroughLatencyProxyTest` → `jsonPath("$", hasSize(...))`
- `owner-search.steps.ts` (ui-test) → `axios.get(...)` then `owners.find(...)` on the body
- `owner.service.ts` → both methods typed `Observable<Owner[]>`
- `openapi.yaml` → `schema: {type: array, items: OwnerDto}`, and the generated `api-types.ts`

**The e2e suite is red right now, before I touch anything.** `OwnersPage.ts` and
`owner-search.steps.ts` select `#ownersTable td.ownerFullName` (camelCase) but the template
renders `class="owner-full-name"` (kebab). `waitForOwnersCount` swallows the timeout in a
try/catch, so it surfaces later as a confusing empty-array diff.

**Orphans left by an earlier revert (`7730901`):** `owner-page.ts` (a Spring-Page-shaped
interface imported by nobody) and dead CSS in `owner-list.component.css` — `.owners-pagination`,
`.owners-page-size`, `#nameGroup`, `.owner-search-input` — for markup that no longer exists.

**Guardrails that will bite:**
- `OpenApiExtractorTest` regenerates `openapi.yaml` from the running app; CI fails on drift.
  `openapi.yaml` is CODEOWNERS-protected (`@victorrentea/elders`) and `.claude/settings.json`
  prompts before AI edits it.
- `api-types.ts` is regenerated by `npm run generate:api` in pre-commit + CI.
- `JpaMatchesDBSchemaTest` (`ddl-auto=validate`) + `DbSchemaExtractorTest` (regenerates `DB.sql`)
  + the `DB.puml` delta guard → a new index needs the migration **and** both regenerated artifacts.
  `db/migration/` and `DB.sql` are CODEOWNERS-protected.
- `PackagesArchTest` / `C3ArchTest` assert the code's subpackages match `docs/packages.puml` and
  `docs/c4model.c3.dsl` **exactly** → do not create a new subpackage without updating both.
- SonarCloud `java:S107` caps a method at **5 parameters**. `listOwners(lastName, page, size, sort)`
  is 4 — fine, but there is no room for a fifth when #24 adds a global search term.

## Open questions — with my recommended answers

### A. Response envelope: raw Spring `Page` or an explicit DTO?
**Recommendation: an explicit `OwnerPageDto`.** Serializing `PageImpl` directly leaks Spring's
internals (`pageable`, `sort`, `first`, `last`, `numberOfElements`, `empty`) into a public
contract, and Spring Boot 3.3+ logs a warning about exactly this because the shape is not
guaranteed stable across versions. Ship the five fields the orphaned `owner-page.ts` already
guessed: `content`, `totalElements`, `totalPages`, `number`, `size`. Mapped via
`ownerMapper.toOwnerPageDto(page)`.

*Alternative:* enable `spring.data.web.pageable.serialization-mode=VIA_DTO` and return `Page<OwnerDto>`
— less code, but the shape is then Spring's to change, not ours.

### B. What is the `name` sort key, exactly?
**Recommendation: `sort=name,asc` maps to `last_name, first_name, id` — all three, same direction
for the first two, `id` always ascending as the final tiebreaker.** The grid shows
"firstName lastName" in one cell, but people expect a name column to sort by surname. Without the
`id` tiebreaker, Harry/Beatrix Potter and George/Wendy Darling can swap between pages and a row
can appear twice or never — the classic unstable-pagination bug.

`sort=city,asc` likewise needs `city, last_name, first_name, id`, otherwise the 6 London owners
are in arbitrary order.

*Open sub-question:* do you want the API key called `name` (matches the column header) or
`lastName` (matches the DB and the existing `lastName` filter param)? **I'd keep `name`** — the
API describes the resource, not the table, and `lastName` is already taken by the filter.

### C. Page out of range — `?page=99` on 3 pages of data
**Recommendation: return an empty `content` with correct `totalElements`/`totalPages`, HTTP 200.**
That is what every paging API does and what Spring Data does natively; a 404 or 400 here would
force clients to special-case a perfectly ordinary race (someone deleted rows while you paged).
The *frontend* separately never strands you there — see E.

Negative `page`: **400**, consistent with decision 5. (The old implementation clamped to 0.)

### D. What happens to `GET /api/owners/count`?
**Recommendation: leave it alone for now, but note it in the issue.** It becomes redundant the
moment `totalElements` ships, and it is the one owners endpoint with `@PreAuthorize("permitAll()")`
— which smells. Removing it is a second breaking change with its own blast radius (it has a test,
`count_ok`). Better as a follow-up ticket than smuggled into #25.

### E. Frontend behaviour on the edges
**Recommendation, all four:**
1. Changing `lastName` **resets to page 0** (this is an explicit acceptance criterion in the
   parent issue #22).
2. Changing page **size** keeps you near your current position rather than jumping to page 0 —
   simplest honest rule: recompute so the first visible row stays visible.
3. If the current page ends up past the end (search narrowed the result set), **navigate back to
   the last non-empty page** instead of showing an empty grid.
4. Column header shows sort direction (▲/▼) and carries `aria-sort` for screen readers; clicking
   the active column toggles direction, clicking a new column starts at `asc`.

### F. Does the search box stay button-triggered?
**Recommendation: yes, out of scope.** Today it is a "Find Owner" submit button with no debounce.
Turning it into a live, debounced, all-columns search is literally issue **#24**, which is still
open. #25 should not eat it. I'll only make the existing button write `lastName` into the URL
instead of into a field.

*But flag:* issue **#35** ("Owner search by last name is case-sensitive and prefix-only") is
marked **closed**, yet on this branch the repository method is still
`findByLastNameStartingWith` — case-sensitive prefix matching. Either #35 was fixed on a branch
that never reached `orange08`, or it was closed in error. **Which?** It matters because the index
I add in G must match the query (`LIKE` vs `ILIKE` need different indexes).

### G. The index — what exactly?
**Recommendation: `V10__index_owners_for_paged_grid.sql` with two plain B-tree indexes,
`owners(last_name, first_name, id)` and `owners(city, last_name, first_name, id)`** — matching
the two sort orders exactly so Postgres can serve `ORDER BY … LIMIT … OFFSET …` from the index.
The first also serves the `last_name LIKE 'x%'` filter.

Honest caveat: **at 28 rows Postgres will seq-scan anyway** and the index buys nothing measurable
today. I'd still add it — the point is that the query plan stays sane when the table grows, and
you asked for it — but let's not pretend it's a performance fix. If we want to *demonstrate* the
benefit, we need a few thousand seeded owners, which is a different conversation.

If #35 turns out to need `ILIKE`, the first index must instead be
`owners (lower(last_name) text_pattern_ops)` or a `pg_trgm` GIN index — hence the question in F.

### H. Test strategy
**Recommendation:**
- **Backend, TDD, red first.** Turn the acceptance criteria into Cucumber scenarios in
  `owners.feature` (page size honoured, default 10, sort by name/city both directions, 400 on bad
  sort, 400 on bad size, stable order across page boundaries with the two duplicate surnames as
  the fixture). Then a `@SpringBootTest` slice for the whitelist/400 logic.
- **Fix the array-shaped assertions** listed in Ground Truth as part of the same commit that
  changes the shape — they are the proof the change is complete, not collateral damage.
- **Frontend unit**: `owner-list.component.spec.ts` needs an `ActivatedRoute` stub that provides
  `queryParams` (the current stub only has `params` — this is a known trap, the old
  implementation hit it too).
- **E2E is mandatory** (Playwright): fix the `td.ownerFullName` selector first so the suite is
  green *before* my change, then add scenarios that drive the paged grid through the browser —
  20 rows per page, click City to sort, page 2 shows different owners, deep-link
  `?page=1&sort=city,desc` restores state. Note `owners.spec.ts` "shows all owners on initial
  load" currently expects all 28 in the DOM and **must** be reworked for a default page of 10.
